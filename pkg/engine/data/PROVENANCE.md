# Data table provenance

This file records the primary source behind each data table in this package
and how the generated ones regenerate.

## `keyboards.go` — keyboard adjacency (qwerty, qwertz, azerty)

**Source: rebuilt from the physical layouts.**

Each layout is expressed as its physical rows (the characters on each row,
left to right) plus a per-row horizontal stagger of half a key-width — the
standard ANSI/ISO physical offset that makes each key sit visually between
the two keys of the row above and below it. The adjacency table itself is
*computed* from those positions: two keys are neighbors when their
Euclidean distance is at most ~1.12 key-widths, which reaches same-row
neighbors (distance 1) and the two staggered diagonal neighbors in the row
above/below (distance ≈1.118), while excluding a same-row key two positions
over or a key two rows away.

The result was sanity-checked against the neighbor *sets* dnstwist's
`qwerty`/`qwertz`/`azerty` tables produce (e.g. both compute `s` on qwerty
as neighboring `{a,d,e,w,x,z}`) to confirm the geometric model reproduces
correct physical adjacency; the Go source that computes the tables is the
only artifact checked in.

## `glyphs_ascii.go` — ASCII look-alike substitutions

**Source: widely known ASCII homoglyphs** (digit/letter look-alikes such as
`0`/`o`, `1`/`l`/`i`, `3`/`e`, `5`/`s`; and the classic multi-character
illusions `rn`→`m`, `vv`→`w`, `cl`→`d`). These substitutions are documented
across many public typosquatting write-ups.

## `glyphs_unicode.go` — Unicode confusable substitutions

**Source: [Unicode `confusables.txt`](https://www.unicode.org/Public/security/latest/confusables.txt)
(Version 17.0.0, Unicode License), inverted and filtered.**

Generated by parsing `confusables.txt`'s `source ; target ; type` records,
keeping only records whose target is a single codepoint in `[a-z0-9]`
(i.e. the character an attacker would want to imitate) and whose source
codepoint falls in a Unicode block plausibly used in a homograph attack:
Latin-1 Supplement, Latin Extended-A/B, IPA Extensions, Greek and Coptic,
Cyrillic (+ Supplement), Armenian, and Halfwidth/Fullwidth Forms. Blocks
excluded by this filter — Mathematical Alphanumeric Symbols, Enclosed
Alphanumerics, Roman Numerals, Canadian Syllabics, and similar — are
technically-confusable codepoints that are either not IDNA-registrable or
not plausible phishing material, so including them would only inflate the
candidate count without adding real risk coverage.

`confusables.txt` has no entries mapping onto plain digits `0`, `1`, `4`,
`7`, `9`, or onto the letters `k`, `m`, `t`, `z` within the accepted blocks
above; those gaps are real properties of the source file, not an omission
in the extraction. `glyphs_ascii.go`'s digit substitutions (`0↔o`, `1↔l/i`,
etc.) cover the digit side of that gap; the letter gap is simply narrower
coverage for those four letters.

The extraction is checked in at `gen/glyphs/main.go` and runs via
`go generate ./pkg/engine/data`. The filter described above is stated twice —
here in prose and there in code — and the code is authoritative: a filter that
lives only in prose has to be *re-derived* rather than re-run, and a
re-derivation landing on a slightly different block set would silently change
which look-alike domains `yatt` generates.

The generated file's header records the exact upstream version and date it came
from, so a stale snapshot is visible rather than merely possible. Regenerating
is expected to produce a reviewable diff: each Unicode release adds confusables.

Coverage was sanity-checked against dnstwist's `glyphs_unicode` table and
ail-typo-squatting's `SIMILAR_CHAR` table: the well-known Cyrillic
а/е/о/р/с/у/х and Greek ο/υ homographs those tools flag are all covered
here.

## `glyphs_idn_by_tld.go` — per-TLD IDN gating

**Source: curated from general public knowledge** of which ccTLD
registries restrict registrations to a single
non-Latin script (so a Latin-confusable candidate could never be registered
there) or have historically not offered broad IDN registration. This is a
conservative starting set, not an audit of current registry policy — see
the file's own doc comment for what an incomplete list costs (nothing but
an extra query that resolves to NXDOMAIN).

Conceptually mirrors what dnstwist's `glyphs_idn_by_tld` table is *for*:
suppressing IDN homoglyph noise under ccTLDs that cannot register them.

## `tlds_common.go` — curated common TLD list

**Source: assembled** from the classic gTLDs (`com`, `net`, `org`, ...),
the short list of gTLDs commonly used as brand extensions (`io`, `co`,
`app`, `dev`, ...), and the ccTLDs of the countries with the largest
internet-user populations.

## `tlds_abused.go` — curated abused TLD list

**Source: assembled** from the TLDs repeatedly named in publicly published
registrar-abuse research (Spamhaus' and Interisle's periodic "most abused
TLD" reports, and similar public reporting) as disproportionately
represented in phishing/typosquatting takedown data.

## `tlds_iana.go` — full IANA TLD list

**Source: [IANA Root Zone Database](https://data.iana.org/TLD/tlds-alpha-by-domain.txt).**
IANA publishes this list specifically for reuse by exactly this kind of
tooling; it is reproduced here verbatim (lowercased) with no modification
beyond formatting. Public domain / no copyright asserted by IANA over the list
of delegated TLDs itself.

Generated by `gen/tlds/main.go` via `go generate ./pkg/engine/data`. The
generated file's header carries IANA's own version line (`Version NNNNNNNNNN,
Last Updated ...`), which is what dates the snapshot.

Note that `IANATLDSet` lives in the hand-maintained `tldset.go`, not in the
generated file — anything placed in `tlds_iana.go` is discarded by the next
regeneration.
